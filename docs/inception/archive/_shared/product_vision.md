# Phasegate v1 — プロダクトビジョン

> **ステータス**: Draft
> **作成日**: 2026-03-10
> **対象**: Phasegate v1（AIDLC Harness v0 の後継）

---

## 1. プロダクト名の正式定義

### 正式名称

**Phasegate** = **G**overned **S**oftware **D**evelopment **L**ife**C**ycle

「ガバナンスされたソフトウェア開発ライフサイクル」を意味する。"Get Shit Done" の頭字語 GSD を内包しつつ、SDLC（Software Development Life Cycle）という業界標準概念と融合させた造語である。

### 命名の意図

| 要素 | 意味 | 由来 |
|------|------|------|
| **G** | Governed（統治された） | AIDLC v0 の品質ガバナンス思想 |
| **SD** | Software Development | SDLC の標準用語 |
| **LC** | Life Cycle | プロジェクト全生涯の管理 |

"Get Shit Done" の精神（速度・実行力・実用主義）を DNA として持ちながら、"Governed" の冠により「品質ゲートなき速度は暴走に過ぎない」という AIDLC の哲学を表現する。略称として「Phasegate」を使用し、口語では "Get Shit Done Life Cycle" と読んでも差し支えない。これは意図的なダブルミーニングである。

### v0 から v1 への進化ナラティブ

**AIDLC Harness v0** は「AI 駆動開発に品質保証の鎧を着せる」ことに成功した。26 の AgentSkills、4 層防御モデル、2-Phase Execution は、AI エージェントが生成するコードの品質を人間の設計意図に従わせる強力な仕組みを確立した。

しかし v0 には致命的な弱点があった。**コンテキストの腐敗**、**逐次実行のボトルネック**、**セッション間の記憶喪失**。品質は守れたが、速度と効率は犠牲になった。

一方、GSD2.0 フレームワークは正反対の強みを持っていた。コンテキストエンジニアリング、Wave 並列実行、セッション管理。速度は出るが、品質の担保は開発者の自己規律に委ねられていた。

**Phasegate v1 は、この二つの世界を一つにする。** GSD2.0 の「オーケストレーションエンジン」を AIDLC の「品質エンフォーサー」の内側に組み込む。速度と品質を二項対立ではなく、アーキテクチャとして両立させる。

```
v0 (AIDLC)        v1 (Phasegate)
品質 ████████████   品質 ████████████
速度 ████           速度 ██████████
効率 ███            効率 █████████
```

## 2. What This Is

**Phasegate は、AI エージェントによるソフトウェア開発の全ライフサイクルを、品質ゲート付きで自律的にオーケストレーションするエンジニアリングツールキットである。**

DDD 設計方法論と 4 層品質防御を核に持ち、コンテキストエンジニアリングと Wave 並列実行によって、設計から実装・検証までを安全かつ高速に駆動する。人間は設計の承認者として介在し、それ以外は AI エージェントが自律的に遂行する。

**対象ユーザー**: AI エージェント（Claude Code, Codex 等）を活用してプロダクション品質のソフトウェアを構築するエンジニアリングチーム。「AI にコードを書かせたいが、品質を妥協したくない」チームのためのもの。

---

## 3. Core Value — 1つだけ残すなら

> **「設計意図とコードの構造的整合性を、機械的に保証し続けること」**

全てのスキルが壊れても、全てのオーケストレーションが止まっても、この 1 つだけは機能しなければならない:

**設計文書に書かれた構造（ドメインモデル、レイヤー境界、テスト仕様）と、実際のコードが乖離していないことを、人間の注意力に頼らず検出し続ける能力。**

これは v0 から引き継ぐ不変の核であり、v1 で追加される全ての機能（Wave 並列実行、コンテキスト管理、セッション管理）は、この Core Value を侵害しない限りにおいてのみ存在が許される。

### Core Value の具体的な表現

| 層 | メカニズム | 守るもの |
|----|-----------|----------|
| L1: ESLint AST 解析 | `no-layer-violation`, `enforce-folder-structure` | アーキテクチャ境界 |
| L2: Pre-commit | Phase Gate, Dependency Validator | 設計→実装の順序と依存方向 |
| L3: CI | Consistency Checker, Coverage Gate | レイヤー間整合性、テスト網羅性 |
| L4: Scheduled | Drift Detector, Lesson Collector | 設計-実装の経時的乖離 |

## 4. ポジショニング

### 競合フレームワークとの差別化マップ

```
                    品質保証の深さ
                    ▲
                    │
            Phasegate ■ │
                    │         AIDLC v0 ●
                    │
                    │
                    │              BMAD ●
                    │
                    │    Speckit ●
                    │
        GSD2.0 ●   │   Taskmaster ●
                    │
                    └──────────────────────► 実行効率・速度
```

| フレームワーク | 強み | 弱み | Phasegate との違い |
|---------------|------|------|---------------|
| **GSD2.0** | コンテキスト管理、Wave 並列、セッション管理 | 品質保証なし、設計方法論なし | Phasegate は GSD の実行エンジン概念を品質ゲートの中に封じ込める |
| **BMAD** | ロールベースのエージェント設計、段階的ワークフロー | コードレベルの品質強制なし、ESLint/Pre-commit 統合なし | Phasegate は「プロンプトで願う」のではなく「コードで強制する」 |
| **Speckit** | 仕様駆動開発、型安全な仕様管理 | オーケストレーションなし、並列実行なし | Phasegate は仕様から実行・検証まで全ライフサイクルをカバー |
| **Taskmaster** | タスク分解と依存管理、PRD からのタスク生成 | アーキテクチャ強制なし、テスト品質管理なし | Phasegate はタスク管理の上位に設計方法論と品質ハーネスを持つ |
| **AIDLC v0** | 4 層防御、DDD 設計スキル群、2-Phase Execution | コンテキスト腐敗、逐次実行、セッション管理不在 | Phasegate v1 は v0 の全ての強みを維持しつつ弱点を解消する |

### Phasegate のユニークポジション

**「コードレベルのアーキテクチャ強制力を持つ、唯一の AI 開発オーケストレーションフレームワーク」**

他のフレームワークは「エージェントに指示を出す」ことに注力する。Phasegate は「エージェントの出力を機械的に検証する」ことに注力する。指示はプロンプトで行い、検証は ESLint・Pre-commit・CI・Scheduled の 4 層で行う。この「信頼するが検証する（Trust but Verify）」アプローチが Phasegate の差別化要因である。

## 5. 設計哲学 — v1 を貫く 5 原則

### 原則 1: 品質ゲート付き速度最適化（Gated Velocity）

> ゲートは通過必須。ゲート間は最大速度。

速度と品質を二項対立として扱わない。Phase Gate・4 層防御・2-Phase Execution が品質のチェックポイントを構成し、チェックポイント間では Wave 並列実行・コンテキスト分離・Model Profile によって最大速度を追求する。

**具体例**: Wave 内の複数 story-implementor は完全並列に実行されるが、Wave 完了後には全 L2 バリデータが通過しなければ次の Wave に進めない。

```
Gate ──── 最大速度 ──── Gate ──── 最大速度 ──── Gate
 │    Wave 1 (並列)     │    Wave 2 (並列)     │
 │    ├─ US-001         │    └─ US-003         │
 │    └─ US-002         │                      │
 └─ Pre-flight          └─ Post-wave           └─ Final
    harness:check-ready    L2 validators          drift-detect
```

### 原則 2: 設計は人間が承認し、実行は機械が自律する（Human Gate, Machine Execute）

> 2-Phase Execution は設計フェーズの聖域。実行フェーズは自律の領域。

AI が最も危険な誤りを犯すのは「何を作るか」を決める瞬間であり、「どう作るか」を実行する瞬間ではない。したがって設計スキル（domain-designer, logical-designer 等）の出力には必ず人間の承認を求め、実行スキル（story-implementor）は承認済み設計に基づいて自律的に動く。

**非交渉**: この原則はいかなる効率化要求によっても緩和されない。Quick Mode であっても、新規ドメインモデルの追加には人間承認が必須。

### 原則 3: コンテキストの鮮度は品質である（Fresh Context = Quality）

> 腐ったコンテキストで書かれたコードは、腐ったコードである。

200K トークンのコンテキストウィンドウは有限資源である。長時間セッションでのコンテキスト腐敗（context rot）は、AI エージェントの判断力を劣化させ、設計意図の見落とし・既存パターンの無視・不整合なコード生成を引き起こす。

**実装**: 各 executor には新鮮な 200K コンテキストを割り当て、必要な設計文書（domain_model.md, logical_design.md, test_design.md）を毎回ロードする。オーケストレーターはコンテキストの 15% のみを使用し、残りを executor に配分する。

### 原則 4: 検証は実行可能コードで表現する（Executable Governance）

> ドキュメントに書かれたルールは破られる。コードに書かれたルールは実行される。

アーキテクチャ原則、テスト品質基準、レイヤー依存方向、フォルダ構造規約 — これらは全て ESLint カスタムルール、Pre-commit バリデータ、CI チェッカーとして実行可能なコードに変換される。人間の注意力や AI エージェントの善意に依存する品質保証は、品質保証ではない。

**具体例**:
- 「ドメイン層は外部フレームワークに依存しない」→ `no-layer-violation` ESLint ルール
- 「テストは AAA パターンで書く」→ `enforce-test-aaa` ESLint ルール
- 「設計文書なしに実装コードを変更しない」→ `phase-gate` Pre-commit バリデータ

### 原則 5: 段階的開示で複雑さを隠蔽する（Progressive Disclosure）

> 入口は簡素に。奥行きは深く。

26 のスキル + Wave オーケストレーション + 4 層防御 + セッション管理。この複雑さをユーザーに一度に見せてはならない。

- **入口**: `/gsdlc:quick` で即座にアドホックタスクを実行できる
- **標準**: `/gsdlc:execute <unit>` で Wave 並列実行が自動的に動く
- **詳細**: 個別スキル（domain-designer, logical-designer 等）を直接呼び出せる
- **設定**: `phasegate.config.json` で全パラメータを制御できる

新規ユーザーは Quick Mode から始め、プロジェクトの成熟に応じて段階的にフルハーネスへ移行する。Brownfield プロジェクトは `harness:scan` → L1 のみ → L2 追加 → L3 → L4 と週単位で防御層を積み上げる。

## 付録: 9 つの非交渉要件（v0 から v1 への不変契約）

以下は Phasegate v1 においていかなる統合・最適化・簡素化の圧力にも屈してはならない要件である。

| # | 要件 | 根拠 |
|---|------|------|
| 1 | **4 層防御モデル** (L1-L4) | Phasegate の差別化要因そのもの |
| 2 | **Phase Gate** | 設計→実装の順序をコードレベルで強制する最後の砦 |
| 3 | **ESLint AST 解析** | import グラフ解析+循環依存検出。プロンプトでは代替不可能 |
| 4 | **テスト品質ルール** | AAA, actual 命名, single-act, no-domain-mocking |
| 5 | **DDD 設計スキル群** | domain-designer 等。設計方法論の核心 |
| 6 | **2-Phase Execution** | AI 安全メカニズム。人間承認ゲート |
| 7 | **Document Split** (inception/product) | 一時的 vs 累積的の明確な分離 |
| 8 | **Cascade Updater** | 下位変更→上位設計への影響伝播 |
| 9 | **Agent-Lesson System** | 主流フレームワークに同等機能なし。独自の革新 |

---

> **このビジョンは Phasegate v1 の全ての設計判断の起点となる。個別の機能設計・アーキテクチャ判断・トレードオフ解決において迷いが生じた場合、Core Value（設計意図とコードの構造的整合性の機械的保証）と 5 原則に立ち返ること。**
