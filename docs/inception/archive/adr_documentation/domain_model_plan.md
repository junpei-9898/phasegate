### 集約候補とその根拠

#### 集約候補1: ADR（Architecture Decision Record）

**根拠**: ADRは本Unitの中心概念であり、独立したライフサイクル（作成→提案→承認→廃止/置換）を持つ。フロントマター（メタデータ）と本文（セクション群）で構成される一貫した整合性境界を形成する。

- **エンティティ候補**: ADR（一意識別子=ADR番号、ライフサイクルを持つ）
- **値オブジェクト候補**:
  - `AdrId` — ADR番号（NNN形式の一意識別子）
  - `AdrStatus` — ステータス列挙型（Proposed | Accepted | Deprecated | Superseded）
  - `AdrFrontMatter` — フロントマター構造（title, status, date, superseded_by）
  - `AdrBody` — 本文構造（context, decision, consequences, alternatives）
  - `SupersededByRef` — 後継ADR参照（Superseded時のみ有効）

**整合性ルール**:
- ステータスがSupersededの場合、`superseded_by`フィールドは必須
- ステータスがSuperseded以外の場合、`superseded_by`は空でなければならない
- ADR番号は全ADR内で一意
- フロントマターのstatusフィールドは4つの許容値のいずれか

#### 集約候補2: ADRテンプレート

**根拠の検討と結論**: ADRテンプレートは「ADRの構造定義」であり、単一のテンプレートファイル（`docs/ADR/template.md`）として存在する。独自のライフサイクルを持たず、ADR集約の構造仕様を定義する静的な参照情報である。

**判断**: 独立した集約とはせず、ADR集約のファクトリパターン（テンプレートに基づくADR生成）の入力として扱う。テンプレート自体のバリデーションはADR集約の構造定義に基づいて行う。

## 3. 設計方針

### 集約の粒度方針

- **単一集約設計**: 本Unitは「ADR」という単一の集約を中心に設計する。ADRは自己完結したドキュメント単位であり、ADR間の参照関係（superseded_by）は値オブジェクトとして集約内に保持する。
- **粒度の根拠**: US-020〜022の3ストーリーは全てADRという単一概念に対する操作（テンプレート整備→作成→ステータス管理）であり、複数集約に分割する合理的な理由がない。

### 値オブジェクト vs エンティティの判断基準

| 概念 | 分類 | 根拠 |
|------|------|------|
| ADR | エンティティ | ADR番号による一意識別。ステータス遷移というライフサイクルを持つ |
| AdrId | 値オブジェクト | 不変の識別子。等値性で比較 |
| AdrStatus | 値オブジェクト（列挙型） | 4つの固定値の中から1つを取る。不変 |
| AdrFrontMatter | 値オブジェクト | title, status, date, superseded_byの構造体。ADRの属性 |
| AdrBody | 値オブジェクト | context, decision, consequences, alternativesの構造体 |
| SupersededByRef | 値オブジェクト | 後継ADRへの参照。AdrIdをラップ |

### ドメインイベント候補

本Unitのドメイン特性（ドキュメント管理、ファイルベース）を考慮すると、明示的なドメインイベント発行は過剰である可能性が高い。ただし以下を候補として記録する:

- `AdrCreated` — 新規ADR作成時（US-021）
- `AdrStatusChanged` — ステータス遷移時（US-022、特にSuperseded遷移時の後継ADR参照検証トリガー）

**判断**: v1実装では、ドメインイベントの明示的な発行メカニズムは不要と考える。ステータス遷移ルールはADRエンティティ内のバリデーションロジックとして実装し、イベント駆動は将来拡張時に検討する。

### Shared Kernelとの関係

- 本Unitは他Unitと共有するドメインオブジェクトを持たない
- `HarnessError`フォーマットは統合契約で定義済みであり、harness-dx Unitが本UnitのADRファイルを`adr_ref`で参照する形で連携する
- ADRフロントマターのYAML構造定義は統合契約（§4.8）で公開済み

### ADRのファイルベース特性への対応方針

ADRはMarkdownファイル（YAMLフロントマター + Markdown本文）としてファイルシステム上に永続化される。この特性から:

- **リポジトリパターン**: ADRの読み書きはファイルシステムアクセスとなる。ドメイン層ではリポジトリインターフェース（Port）を定義し、インフラ層でファイルシステムアダプターを実装する
- **シリアライゼーション**: ADRエンティティ ⇔ Markdownファイル（YAMLフロントマター + Markdown本文）の双方向変換をアダプターが担当
- **バリデーション**: フロントマターのスキーマ検証はドメイン層の責務。ファイルI/Oはインフラ層の責務

## 4. QA（不明点・確認事項）

### [Question] Q1: ADRテンプレートの管理粒度

ADRテンプレート（`docs/ADR/template.md`）をドメインモデルとして明示的に管理すべきか、それとも単なる静的ファイルとして扱うべきか。

**背景**: テンプレートはADRの構造定義であり、テンプレート自体の変更はADR全体の構造に影響する。一方で、テンプレートは単一ファイルであり、複雑なライフサイクル管理は不要。

**推奨案:** テンプレートは独立した集約とせず、ADR集約のファクトリパターンの入力（構造仕様）として扱う。テンプレートファイルのバリデーション（必須セクションの存在確認）はADRファクトリの責務とする。テンプレート自体のCRUD操作は本Unitのドメインモデルの対象外とする。

[Answer]
推奨案を採用。

### [Question] Q2: ADR番号の採番ルール

ADR番号（NNN形式）の採番は「既存ADRの最大番号+1」の自動採番とするか、手動指定を許容するか。

**背景**: US-021で初期10件を一括作成する際、番号の連続性と一意性を保証する仕組みが必要。将来的にADRが削除された場合の欠番処理も考慮が必要。

**推奨案:** 自動採番（既存最大番号+1）をデフォルトとし、手動指定は許容しない。欠番は許容する（削除されたADRの番号は再利用しない）。これにより採番の一意性が保証され、番号の時系列順序が維持される。

[Answer]
推奨案を採用。

### [Question] Q3: フロントマターバリデーションの実行タイミング

US-022のAC-4「ADRフロントマターのバリデーションテスト」について、バリデーションは(a)ADR作成・更新時のドメインロジックとして実行するか、(b)独立したバリデータコマンドとして実行するか、(c)両方か。

**背景**: 統合契約§4.8でADRフロントマター構造が定義されており、harness-dx Unitが`adr_ref`で参照する。フロントマターの整合性はシステム全体の信頼性に影響する。

**推奨案:** (c) 両方。ADRエンティティ生成時にドメインバリデーション（不正ステータス値、Superseded時のsuperseded_by欠如等）を実行し、加えてCIレベルで全ADRファイルのフロントマター一括検証テストを用意する。これにより作成時の即座のフィードバックと、既存ADR群の継続的整合性チェックの両方を実現する。

[Answer]
推奨案を採用。

### [Question] Q4: ステータス遷移の制約

ADRのステータス遷移に制約を設けるべきか。例: Proposed→Accepted は許可、Accepted→Proposed は不許可（逆行禁止）。

**背景**: US-022ではステータス値の定義とSuperseded時の後継参照が要件として明記されているが、遷移ルール（どの状態からどの状態への遷移を許可するか）は明示されていない。

**推奨案:** 以下の遷移ルールを設ける:
- `Proposed → Accepted` : 承認
- `Proposed → Deprecated` : 提案段階での棄却
- `Accepted → Deprecated` : 非推奨化
- `Accepted → Superseded` : 後継ADRによる置換
- `Deprecated → Proposed` : 非推奨からの再提案（例外的に許可）
- その他の遷移は不許可（例: Superseded → Accepted）

ただし、初期実装ではステータス遷移の制約を厳密にせず（任意遷移を許可）、Superseded時のsuperseded_by必須チェックのみを実装する軽量アプローチも検討に値する。

[Answer]
推奨案を採用。

### リスク

| # | リスク | 影響度 | 確率 | 軽減策 |
|---|--------|--------|------|--------|
| R1 | ADRの内容品質がドメインモデルでは保証できない | 中 | 高 | ドメインモデルは構造的整合性（フロントマター必須フィールド、ステータス値の有効性）のみを保証する。内容の品質は人間レビューに委ねる |

| R3 | ADR間のsuperseded_by参照が循環する可能性 | 中 | 低 | バリデーション時に参照先ADRの存在確認を行い、循環参照チェックを将来的に追加する |
