# 設計方針

<!-- @work-item-id WI-220 -->

## 制御を置く場所

| 関心 | 方針 |
|---|---|
| 信頼ルート・保護設定の書換 | 既存の事前拒否と管理コマンド／人間の正規操作を維持。ADR-038/039/041を尊重 |
| 設計前提や共有契約を壊す実装 | 影響する範囲だけ止め、根拠・上位判断対象・再開条件を提示 |
| 読み取り・調査・inception計画 | 新たな実装前提条件を課さない。未知のshellを読み取りと決めつけない |
| 設計の意味的整合 | agentのレビューと証跡で扱う。タグやチェックボックスを品質判定器にしない |
| lint・構造検証 | 編集後の対象報告と、完了／CIの全体検証を使い分ける。必要な検証そのものを消さない |
| 変更履歴 | WI・ADR・Gitに理由と検証を残す。productは現行仕様を統合更新する |

## 責務の整理

`agent-integration` は入力正規化・対象抽出・実行／報告、`config-foundation` は旧設定の解決、`harness-api` と `validator-system` は共通の検証経路、`phase-dependency-model` と `world-model` は根拠のある依存・反映状態、`quick-mode` は変更分類、`skill-quality` は手順支援を担う。skill名・自己申告のcaller情報を認可に使わない。

設定の新しい独立キーはスキーマ・管理更新経路・旧値対応表を確定してから追加する。新キー不在時は旧設定を読む。`cascadeUpdate=false` でpost hookが無効だった利用者を、更新だけで突然有効にしない。互換処理は設定入口に一度だけ置き、各UseCaseへ新旧分岐を広げない。

## hookの軽量化

読み取りと無効化済みhookではlint子プロセスを起動しない。書込み対象をCLIまで伝える。ただし解析対象と報告対象は異なる。依存グラフや未使用判定は必要な全体コンテキストを読み、編集後の報告のみ対象へ絞る。WI-390で扱った単一ファイル解析由来の誤検出を再導入しない。

`--fast` は実装とhelpの契約を一致させる。500msを無根拠に維持・延長せず実測する。タイムアウトは完了成功ではない。子プロセス回収、診断、次の明示検証を定義し、自動再試行で作業を塞がない。正常な無効化skipを毎操作保存しないが、異常入力・予期せぬ失敗の診断は残す。

## 対象WIと変更リスク

実ファイル、管理されたセッションのWI/Unit/有効期限、設定、明示依存を根拠に対象を特定する。対象WIと共有契約への依存閉包を検証し、無関係なdraft WIを一律にロック理由にしない。複数WI・共通ファイル・対象不明の場合を独立にテストし、対象不明を迂回経路にしない。

内部抽出・adapter追加と、公開API・業務不変条件・認可・データ契約変更を区別する。パスだけの推定は補助情報とする。新分類器で確定できないものは、まず助言と既存判断の比較に留める。黙って新しい強制ブロックを増やさない。

## 双方向の設計伝播

1. 下位の発見をWIに記録する（観測、影響する前提、関連設計、代替案）。
2. 既に合意された意味を変えない整合修正はagentが進める。
3. 目的、契約、不変条件、Unit境界に影響するときは上位判断を求める。止めるのはその判断に依存する作業だけ。
4. 承認／却下／代替案の決定を記録し、必要な上位設計から下位設計・テストへ反映する。
5. 更新対象revisionで再検証し、解決済み理由では再ブロックしない。後続変更で前提が変われば再評価する。

「参照がある」「前提が変わった」「レビューした」「テストした」を区別する。新しい必須台帳を全利用者へ導入するのではなく、既存WI・ADR・World Modelの明示依存／pinを利用する。両端の変更で鮮度を再評価し、タグの追記だけでsemantic reviewを完了にしない。World Model未導入・legacy baseline・waiverの既存契約は保持する。

productの重複・矛盾した旧説明は統合・置換して現行設計を読みやすくし、変更理由はWI/Gitで残す。固定3段階承認や一律追記しか許さない手順は、判断の必要な境界に絞る。
