§1.5 ── 二巡目
逆張りレビューと階層実験が、初版の前提を 2 箇所修正した
修正 1: 本文書自身の誤り（sol レビュー・ソース実検証 11 箇所）
P10 は事実誤認で不要 — phasegate には ADR-019（AI-independence boundary）が既に存在し、「LLM/AI 判断が validation の一部になることは決してない」と本提案より強く規定していた。「較正閾値を超えれば blocking 可」とする本提案はむしろ緩和方向＝取り下げ。
P2 初版は自分の掲げた Goodhart 法則に違反 — 「Read イベントの有無」を検査すれば limit: 1 の形式的 Read で満たせる。読取強制ではなくRead イベント強制を作るところだった。
P3 は「coverage」の二義性を混同 — coverage_report.md は AC/ドメイン/UseCase/API の設計カバレッジ（意味的主張）であり、実行時の行カバレッジではない。「ハッシュ＋再実行」で証明できるのは後者のみ。
修正 2: 「skill 規範文＝死」は一枚岩ではなかった（階層 A/B 実験）
同日の盲検 A/B 5 本（生成 88 本・38 ペア・全て事前登録の凍結基準つき・系列レポート）で、skill 部品の効きは内容カテゴリでなく機能で分かれた:

判断の圧縮（verdict 配線・「〜は NG」機械ルール・強制フロー）: Sonnet W=+8 ／ Fable W=−4 で符号反転。ルールの精度がモデルの判断を上回る帯域でだけ利得＝能力に対して逆 U 字。失敗様式は「例外の誤爆」（意図的な設計ガードを『直すべき違反』と誤誘導）。
判断の拡張（読むだけの準備ターン・事実の棚卸し・未確認の開示）: 圧縮を抜いた B′ が Fable で W=+4＝モデル非依存に有効。開示規律だけは全階層を貫いて効いた。
phasegate への含意で最も大きいのは、bundled skill が元来 Sonnet 委任前提（frontmatter model: sonnet・delegate 機構）で書かれている点──「圧縮の多い厳格 skill × Sonnet ワーカー」という phasegate の元々の組は、この実測ではむしろ正当。害が出るのは委任を切って frontier が直接実行する構成（本プロジェクトの運用がまさにそれ）。したがって初版 P8 の「規範を削る監査」も、sol の「契約文書として残せ」も、どちらも部分的に正しくなかった──正解は機能分類＋実行階層での着脱（P8 v2）。

留保: 階層実験の判定者は AI 代理（Codex sol）・n=6/セル（Sonnet 完全版のみ 20）・skill 1 個・コーディングレビュー 1 分布＝信号レベル。このプロジェクト自身の実測で「AI 判事はユーザー選好と不一致（7〜8/15）」が確定している以上、この留保は飾りではない。v2 が信号だけで断行した改訂は「主張を弱める方向」（削除→分類・強制→計測・ADR 新設→既存 ADR への追記）に限定した。
§2 ── 詳細
各提案の根拠・現状・変更
P1
「案内どおりにやれば直る」を、機械検証された不変条件にする
実測
40 本超の実験で生き残った指示文の型は 2 つだけ──①モデルが知らない事実、②構造の中の「今やる 1 手」。HarnessError の次アクションは②そのもの＝phasegate が持つ唯一の生きたプロンプト面であり、ここの品質がエージェント自己修正（README の中核価値）を直接決める。

現状
本日の実地で、この面の破れを 3 系統確認した。(a) 純 Python リポで L3-003 が vitest --coverage 等で… と JS 前提の指示を出し、正解（project.languages 宣言）へ誘導しない（#39）。(b) L2-016 自身が案内する ungated-legacy マーカーを付けても、Stop hook が叩く complete-check は severity 集約（isEffectivelyPassed）を通さないため赤のまま（#38・command-dispatch-service.ts:292）。(c) コード内で opt-out として文書化された coverageThreshold: null がスキーマで拒否され到達不能（#37）。3 つとも「phasegate 自身の案内に従うと直らない／壊れる」型。

変更
① 集約判定を 1 つの関数に一本化し、validate / complete-check / ci-check / pre-commit / hook の全コマンドがそれを通ることを regression で固定する。② エラーメッセージ契約を CI で検証する: 各 validator の fixture に「エラー → suggested action を機械適用 → 再実行で pass」の往復テストを足す。suggested action がそのプロジェクト状態で実行不能（Python リポに vitest）または解消に至らないなら、それは fixture 落ちとする。「案内の正しさ」を人間レビューでなくテストが担保する形に。

v2 改訂
sol の条件を採用: 「1 関数への一本化」は粗い──status のように failure を表示しつつ exit 0 を返す契約のコマンドが実在するため、共有するのは実効 severity・集約・コマンド別 exit 方針の 3 点。往復テストは remediation を mechanical / ai-assisted / manual に分類し、機械適用可能なもののみを対象にする（全 suggestion の機械往復は成立しない）。

P2
読取の計測から行動トリガー介入へ（v2 で三段化）
実測
Epic L で最大の陽性: 回答前に「読むだけの準備ターン」を強制すると十分率 40% → 70%（同計算量対照は不動＝効果は「読む」行動そのものに帰属）。トリガー側も「1 度も Read せず回答」の検知は的中率 87.5%で、素の状態の 28.6% がこれに該当。一方「必読」と書くだけの規範は部分服従で、逐語指示は 0/4 で無視される。「読め」と書くことと読まれることは別──読んだかを見る機構だけが効いた。

現状
phase gate は設計文書の存在を検査する。存在 ≠ 読取: 設計が揃っていても、エージェントがそれを読まずに実装を始める経路は開いている。bundled skill はこの穴を規範で塞ごうとしている（story-implementor 注意事項「設計文書を確認せずに実装を開始しない」= 死んだチャネル）。

変更
hook 基盤はすでにツールストリームを見ている。PostToolUse で当該セッションの Read 対象を記録し、PreToolUse は gated path への最初の実装 Write 時に「その gate の requires 文書が今セッションで Read されたか」を検査 → 未読なら HarnessError で「今やる 1 手: docs/.../logical_design.md を読め」を返す。実装は行動ログの照合のみ（意味判定なし）＝87.5% チャネルの適用域内。設計上の注意 2 点: (a) G2′ の教訓どおり浅い読取制限で代替しない（読取上限 5 件では効果が 43〜50% に縮んだ）──強制するのは「読んだか」だけで読み方は縛らない。(b) レイテンシ実測 2〜3× の前例があるため、opt-in で開始し Quick Mode では免除する。

v2 改訂
二方向から修正が入った。① sol（Goodhart）: 「Read が発火したか」だけの検査は limit: 1 の形式 Read で満たせる＝ blanket 前提条件として課すと読取イベント強制に堕ちる。hook 基盤にも現状不足がある（PostToolUse の情報が細い・Bash / MCP 経由の読取は不可視・セッション境界と subagent の扱いが未定義）。② 階層実験: 読取強制の価値は「読まずに断定する」欠損の有無に依存し、欠損のない実行者には強制コストだけが残る（Fable で W=−4 と同型）。→ 設計を三段に改める: (1) telemetry のみで読取行動の実分布を測る → (2) 行動トリガー介入（WI-101 型: 「Read 0 のまま gated Write」を検知した時だけ HarnessError で 1 手を返す。読取強制下では発火 0/28 だった通り、欠損のない実行者にはそもそも発火しない＝階層検出なしで自動的に安全）→ (3) enforcement は計測が正当化した場合のみ opt-in。初版の「最初の Write 前に必ず既読を要求する」は取り下げ。

P3
attestation を「報告の形」から「再導出可能な証拠」へ
実測
法則 1（Goodhart）: 検証を義務化すると報告が痩せ、差し戻すとコミットに嘘が残り、自動選抜は中身が捏造の「詳細な検証レポート」を選ぶ。対策は一貫して「報告ではなく成果物を検証する」。World Model はこれを正しくやっている（導出レポートは不変・判定は常にコーパスから再導出・手editしても結果が変わらない）。

現状
L2-016 は coverage_report.md の ✅ 主張に attestation ID を要求する＝報告の参照形状のゲート。README 自身が「independent evidence re-execution is L3's future scope」と留保している。つまり現状の均衡点は「よく整形された報告を書けば通る」──Goodhart 面がそのまま残っている。細部でも、adapter は「✅ を含む行」をすべて主張として数えるため（file-system-coverage-attestation-gating-adapter.ts）、説明コメント内の ✅ まで主張化する脆さを本日実地で確認した。

変更
attestation ID の解決先を「再導出可能な証拠」に規格化する: カバレッジ成果物のハッシュ＋再実行コマンドを封入し、L3 が World Model と同じ流儀で証拠を独立再計算して照合する（roadmap の前倒し）。短期では、主張抽出をテーブル行など構造化された位置に限定し、「どの行が主張として数えられるか」を仕様に明記する。

v2 改訂
sol の 4 条件を採用: ① coverage_report.md が扱うのは設計カバレッジ（意味的主張）で、ハッシュ＋再実行で証明できるのは行カバレッジ等の機械的成果物のみ──二義を仕様で分離する。② 方向を反転する: free-form Markdown を検証するのでなく、requirements matrix・テスト結果・coverage provider からレポートを生成する（生成物なら同一性検証の適用域に入る＝World Model と同じ流儀）。③ attestation に埋め込まれた再実行コマンドを validator が実行してはならない（command injection 経路）──再実行コマンドは phasegate 側の固定レジストリから引く。④ 現行の attestation ID は story ID を指す＝意味論変更は breaking であり、既存 v1/v2 スキーマとの migration 設計を含める。

P4
validator を「同一性／行動／意味」で三分類し、意味系は advisory 既定にする
実測
法則 7: 機械検証が届くのは同一性（ハッシュ・スキーマ・存在 = 4/4）と行動（読んだか = 87.5%）まで。意味（主張は真か・テストは良いか）は 2 部品とも死亡──主張検証器は検知 4/7・誤検知 3/7、形状からの不十分検知は recall 42.9%（基準 80%）。しかも誤検知は「忠実な言い換え」への過剰反応だった。

現状
L3-006（injection-scan）は advisory 限定で、これは正しい自制。一方 L2 test-quality の「semantic AAA・assertion 強度・実装ミラーリング検出」は意味照合の側にあり、ブロッキング層（pre-commit）に置かれている。実測に照らせば、この型の検査は狭い上限＋偽陽性コストを構造的に持つ──偽陽性のブロックは「過剰警戒の停滞」（実測された敗因型）をエージェント側に誘発する。

変更
全 validator に measures: identity | behavior | meaning の分類をメタデータとして付け、意味系はブロックでなく warning を既定にする（L3-006 と同じ位置づけへ）。ブロックに残したい検査は、意味でなく構造の代理指標に書き換えられないかを個別に検討する（例: 「assertion が実装定数を参照している」は AST の同一性検査として書ける）。分類は ADR として文書化し、新規 validator の設計審査基準にする。

v2 改訂
sol 反対を受けて縮小: L2-003 系は既に warning を出しており、「意味系がブロックしている」ように見える主因は #38 の集約バグ──P1 を先に直さず P4 を執行すると severity 側と二重補正になる。v2 の提案は「全 validator の測定対象インベントリ作成」まで（一括 advisory 化は撤回）。分類軸も単軸でなく、証拠の出所・権威・偽陽性率・バイパスコストの複数軸が実用的（sol 提案）。なお階層実験の「機械ルールは例外で誤爆し、強い実行者ほど素の判断を上書きして害になる」は、意味系 validator の偽陽性が持つ構造リスクの同型の裏書きであり、インベントリ後の再検討材料として残す。

P5
自己修復路の保証と、遮断スコープの最小化
実測
本日の実地: 不正 config（しかも自身のコードが opt-out として文書化する値）で pre-tool-use hook が Bash/Write/Edit を全遮断し、config を修復する編集自体が遮断された。echo test すら通らず、並行セッションも巻き添え全停止。皮肉にも missing config は fail-open のため「config 削除」が唯一のセッション内復旧手段だった（#40・#31 の同種再発）。さらに doctor はこの状態を診断できず、config 不在は GREEN と報告する。

現状
config 検証が dispatch より上流で fail-closed（main.ts:1868/1945）。ゲートは「非合法手を作る」仕組みとして正しいが、修復と診断まで非合法手にしている。これは実測された敗因型「過剰警戒の停滞」の harness 版でもある──守るべき対象と無関係の操作まで止めると、系全体が停滞する。

変更
不変条件を 3 つ立てる: ① phasegate.config.json 自身への編集は常に許可（自己修復路）。② doctor はどんな config 状態でも起動し、不正 config を「診断結果」として報告する（不在 GREEN もやめ、「config 不在＝既定で fail-open 動作中」と明示する）。③ hook の遮断は gated 操作（保護パスへの書き込み等）に限定し、無関係な Bash は素通しする。missing=fail-open / invalid=fail-closed の非対称も、どちらかに統一して文書化する。

v2 補強
sol 賛成・最優先。2 点精緻化: (a) 「missing / invalid の統一」は雑──config 状態（missing / invalid / valid）× 操作クラス（自己修復・診断・gated 書込・無関係操作）の許可表として仕様化する。(b) 「config 自己編集は常に許可」は広すぎる（valid 状態で守るべき設定が無防備になる）──自己修復例外は invalid / missing 状態の recovery に限定する。

P6
逐語依存の排除 — 機械が書けるものは機械が書く
実測
法則 3: 「一字一句復唱せよ」型の指示は系統的に無視される（識別子 1/4・アクション 0/4）──それでいて作業の中身は正しく継続する。字面の服従を前提にした設計は、能力の問題ではなく性質の問題として壊れる。

現状
commit-msg hook は Work-Item: WI-XXX trailer を機械検査する（検査側は正しい）。しかし trailer の生産はエージェントの字面服従に依存しており、忘れるたびに reject ループが回る。skill 内の固定レポートテンプレート（story-implementor の計画ファイル構成等）も、下流が機械で読むならドリフト前提で壊れる。

変更
① prepare-commit-msg hook で trailer をセッション文脈（active WI / .phasegate/session.json）から自動付与し、エージェントの服従を不要にする（検査は防御として残す）。② skill 出力を機械が読む箇所は、markdown テンプレートでなくスキーマ検証つき構造化ファイルに変える。人間だけが読む箇所はドリフト許容と割り切る。原則: 固定文字列が必要な場所では、プログラムがそれを書く（managed section で既にやっている流儀の全面化）。

v2 補強
sol 条件を採用: session.json は stale・複数 WI・並行セッションで誤 trailer の源になり得る──自動付与は WI が一意に導出できる場合に限定し、曖昧なら付与せず失敗させて 1 手を返す。階層実験は方向を追認: 出力形式の字面服従は frontier でも不安定側（強制フロー・逐語形式は B′ で除去された部品）＝「機械が書く」への移行が唯一の安定解。

P7
リリースゲートに「実分布 holdout」を足す
実測
法則 5: 調整に使ったデータでの改善は初見データで消える──そして「fixture 24 件 all green」の検証器が、実分布の回顧監査では検知 4/7 で落ちた（fixture green ≠ 実分布再現率）。phasegate 自身にも同じ構造が出た: 単体テストは green のまま、新規インストール実機では typescript@7 解決で全コマンド即死（#34）、純 Python リポでは fail-closed（#37/#39）、--with-husky/--with-ci は dead flag（#36）。

現状
検証の主体が bundled fixture と自リポの dogfood（TS リポ）に寄っており、「TS 以外」「新規環境の依存解決」「案内どおりの操作列」が holdout になっていない。

変更
凍結した実リポ corpus（最低: 純 Python・Go・monorepo・docs 無しリポ）に対し、リリース前 CI で「クリーン環境の npm install（lockfile なし・最新 peer 解決）→ install --apply → doctor → validate → uninstall」を実走させる。README が謳う全フラグは、このパスで効果の有無までassert する（dead flag 検出）。これは Exocortex 側で確立した release-smoke（公開エントリを実 subprocess で起動する regression）と同じ型。

v2 補強
sol 賛成・2 点精緻化: (a) 対象は checkout 直実行でなく npm pack した tarball（#34/#36 型の packaging 欠陥は tarball にしか現れない）。(b) 「lockfile なし・最新 peer 解決」は非決定でリリースを止め得るため 2 層に分離──凍結依存で走るrelease gateと、最新解決で走るscheduled canary（落ちたら issue 化・リリースは止めない）。名称も「holdout」でなく実分布リリーステストが正確（調整に使えば holdout 性は消える）。

P8
skill 部品の機能分類 — 拡張は共通装備・圧縮は委任先階層で着脱（v2 全面改訂）
実測
初版の前提「規範の言い換え＝死んだチャネル」は、階層 A/B 実験で解像度不足と判明した。同一 skill 改修が Sonnet で W=+8・Fable で W=−4 と符号反転し、悪化の原因部品（機械ルール・verdict 配線＝判断の圧縮）を抜いた変種は Fable でも W=+4。判断の拡張（準備ターン・棚卸し・未確認の開示）はモデル非依存に有効で、開示規律だけは全階層を貫いた。つまり skill 部品の生死は「規範か事実か」でなく「判断を代替するか・判断材料を増やすか」で決まり、圧縮部品はルールの精度が実行者の判断を上回る帯域でだけ利得になる（逆 U 字）。

現状
bundled skill は元来 Sonnet 委任前提で設計されている（frontmatter model: sonnet・delegate 機構）──BLOCK/WARN 基準や verdict 配線の多い厳格 skill × Sonnet ワーカーという組は、この実測ではむしろ正当な組み合わせ。問題は変種が 1 つしかないこと: 委任を無効化して frontier が直接実行する構成（本プロジェクトの CLAUDE.md User Section がまさにそれ）では、同じ圧縮部品が実測上害側に回る。story-implementor の phasegate session begin という CLI 強制点は階層非依存の構造部品で、これは変えない。

変更
① 29 skill の各行を機能分類する: 圧縮（verdict 配線・「〜は NG」・強制フロー・チェックリスト合否）／拡張（準備ターン・棚卸し・開示・「観測を強制し判断は委任する」）／機械化可能（hook/validator へ移す: Unit 越境は @unit×パス照合、配置規則は既存 L1/L2 で冗長）。② 変種を 2 つ持つ: 圧縮込みの厳格版（B 型）と拡張のみ版（B′ 型）。選択は delegate 設定に連動させる──Sonnet 委任時は B 型・委任無効（frontier 直実行）時は B′ 型。圧縮ルールの B′ 側への書き換え先は「観測の強制＋判断の委任」（例:「具象依存を列挙せよ。妥当性は文脈から判断せよ」）。③ この機能分類を skill-creator の設計審査に組み込む。

v2 留保
sol は初版に対し「規範＝死だから削除、は外挿過剰（skill は人間・レビューの契約文書でもある）」と反対していた──階層実験はこの反対を部分的に支持しつつ精緻化した形（削除ではなく分類・着脱が正解）。ただし根拠実験は AI 代理判定・n=6/セル・skill 1 個 1 分布の信号レベル。よって執行順は変えず（sol 順で最後段）、着手時は削除を伴わない「分類インベントリ＋B′ 変種の試作 1 本」から。

P9
CLAUDE.md 管理セクションを「事実・決定・ゲート接続」型へ／user-section 不可侵を回帰テスト化
実測
CLAUDE.md は行ごとに生死が違う混載コンテナ: ゲート接続コマンド＝生／決定・却下の記録＝生／コマンド一覧＝品質 ±0（時短のみ）／必読リスト・規範手順＝死または部分服従。最も価値が高いのはユーザーの決定記録──そして本日、install --apply がまさにその user-section を placeholder で上書きした（#35）。教訓の言葉で言えば「最も生きたチャネルを、ツールが自ら破壊した」。

現状
managed section はコマンド一覧＋手順規範が中心。user-section 保全は実装意図としては存在する（refresh-claude-md は保全を明記）が、install --apply 経路で破れた＝経路網羅の regression がない。

変更
① user-section 保全を全書き込み経路（install/reconcile/refresh/ci:auto-refresh）の共通 regression にする（byte 同値 assert）。② managed section の中身を再設計: ゲート接続コマンドと「エラー時は list-errors」型の 1 手は残す、必読リストは P2 の読取検知が入るなら削減、手順規範は対応するゲートがあるもののみ「ゲートの説明」として書く。書式指定（trailer 等）は P6 で機械付与に移す。

v2 補強
sol 賛成・順位 2。根本原因を特定済み: CLAUDE.md では user-section が managed block の内側に置かれ（テンプレート構造由来）、AGENTS.md では外側にある──この非対称が #35 の構造因。byte 同値 regression（①）は対症で、本筋はuser-section を managed block の外へ移す構造修正＋一回性 migration。

P10
ADR 化: 「較正なき LLM 判事は導入しない」 — 取り下げ（v2）
実測
法則 5/6 自体は変わらない: AI 判事は人間盲検と 2 回とも不一致（8/15・7/15）で定数戦略を下回り、判事プロンプト較正も dev→holdout で崩壊、自分の属する系を系統的に甘く採点した。

現状
初版の前提「phasegate に該当 ADR はまだ無い」が事実誤認だった（sol がソース検証で指摘）。ADR-019（AI-independence boundary）が既に存在し、「LLM/AI 判断が validation の一部になることは決してない。将来例外を設ける場合も non-blocking・attestation 対象外」と規定している──「較正閾値を超えれば blocking に使える」とする本提案より強い禁止であり、提案はむしろ緩和方向だった。

処置
新 ADR は作らない。残る価値は 1 つだけ: ADR-019 の rationale に Exocortex の実測根拠（不一致 7〜8/15・定数戦略以下・自陣過大評価バイアス・dev→holdout 崩壊）を追記する小 PR。なお本 v2 が依拠する階層実験の判定も AI 代理（Codex sol）であり、この法則の留保はそのまま本文書自身に適用される（§1.5）。
