# Phasegateの価値を磨くための改善検討

作成日: 2026-09-20。状態: 提案・未承認。WI未割当の横断戦略であり、実装着手・規約変更・新しい強制化の承認ではない。

## 1. 結論

次に磨くべきものはゲートの数ではなく、**変更に関係する設計意図を取り出し、影響と必要な判断を説明し、検証済みの成果へつなぐ能力**である。

価値の表現案は「エージェントの実装速度を保ちながら、設計意図を失わずに変更を積み重ねられるセーフティネット」。現行の構造的整合性という中核価値を置き換えず、その利用者側の成果を表す。文書作成数・拒否数・スキル数を成功指標にしない。

今回の調査では実装・設定・既存の承認状態を変更しない。WI-220はユーザーが実施分について一区切りを了承したが、未達3点の免除・全条件達成・公開承認とは解釈しない。

## 2. 根拠と現状の限界

以下はローカルの現行文書と選択した実装の読取に基づく。全機能の再監査や最新候補の再テストではない。競合比較・外部製品の現状評価は行っていない。

| 観察した根拠 | 判断 |

| [全体像](../../product/product_overview.md)、[詳細コンセプト](../../product/harness_product_overview.md) | 中核は設計とコードの構造的整合性。ゲート間の速度、段階導入、自己修正可能なエラーも元来の原則。新規のオーケストレーション基盤は不要 |
| [配置規約](../../folder_management_rules.md) | inception→product→srcの正本構造は維持する。下位の発見は上位への変更提案を経て反映する。srcの結果で上位を無断上書きしない |
| [WI-220監査](../_cross/WI-220/acceptance_audit.md) | 復旧・互換・相対性能には改善の証拠。絶対500ms、広い意味的影響判定、読取比較の候補1誤認は未達。少数試行でモデル品質低下の原因を断定も否定もしない |

## 3. 改善候補と優先順位

### A. 今回の変更に必要な前提を短く提示する — 最優先

**価値:** エージェントが上位文書を常時覚えていることに依存しない。大量の常駐プロンプトを増やさない。

対象WI・変更パスを起点に、関連する上位前提、Unit境界、共有契約、未解決の判断、確認すべきテストを一つの読取ビューで返す。根拠のファイル・節・内容digest、対象revision、収集範囲と不足を示す。構造的に結び付く範囲と、人間が確認すべき意味上の候補を分ける。

- 既存World/traceability/phase-dependencyの正本とconsumer-owned adapterを利用する。コンテキスト管理サービスや第二の依存台帳は作らない。
- 最初は明示的な読取操作とする。自動表示は有用性と費用を確認後、作業開始・対象変更時などに限定する。毎Writeで全体を再読込しない。
- World無効・参照欠落・custom root・対象不明でも、新しい拒否を追加しない。「取得不能」と取得範囲を返し、既存ゲートはそのまま動かす。
- 短い要約と詳細参照を分け、上限超過時は省略件数を明示する。文書本文を権限や実行命令として扱わない。

**成果物:** 最小出力契約、既存入口との統合設計、CLI/agent表示、参照・鮮度・省略のテスト。

**検証:** 上位文書を覚えていない新規セッションに同じ課題を与え、必要前提の参照率・回答正確性・探索回数・出力長・時間を比較する。上位文書の変更、rename、未追跡ファイル、古いdigest、依存欠落、World OFFをfixture化し、古い前提を現行として提示しないことを確認する。

### B. 上位への影響を「判断できる形」で提示する — 差別化の中心

**価値:** エージェントの気付きだけに依存せず、上位への相談漏れを減らす。ただし完全自動の意味判定を約束しない。

実差分にAの前提を接続し、「何が変わった／どの契約・利用者が影響し得る／確認先／何を決める必要がある」をまとめる。明示制約違反、意味上の候補、情報不足を分離する。

- 初期対象は共有API・設定既定値・保存形式・権限条件など、契約が明確な少数ケースに限定する。型が変わらない動作変更も評価用corpusに含める。
- 既存World義務・差分助言・cascade手順を接続し、同じ事象の警告を重複表示しない。LLM判定を必須のゲート依存にしない。
- 承認が必要な変更では、継続可能な調査・設計作業と、判断待ちの変更を区別する。新たな停止範囲の導入は別途明示承認とする。
- 判断は既存WI decision logに根拠と対象digestを残す。承認後に関係する前提が変われば再確認候補にする。タグ追記・pin更新を意味的承認の代わりにしない。

**成果物:** 根拠付き影響レポート、承認/却下/代替案の既存記録への導線、正例・負例・unknownの評価corpus。

**検証:** 事前に答えを決めた上位影響ケースと無影響の内部変更で、検出漏れ・誤警告・unknownを別集計する。「上位へ相談せよ」と課題文で教えず検出を評価する。承認・却下・前提再変更から必要成果物の更新と再開まで試す。助言失敗を既存許可の拒否へ変換しない。

### C. エラーを「再開までの案内」にする — 安全性の最優先

**価値:** 必要な拒否は残し、エラーループと自己流の迂回を減らす。

既存のHarnessError/doctor/nextActionに、発生元・適用規約・修復対象・正規の操作・必要な権限・再確認方法・再開条件を揃える。Phasegate、外部hook、環境不足を区別し、原因が未確定なら断定しない。

- 代表ケースから診断表示を揃える。新しい自動修復エンジンや包括的retry機構は作らない。
- 同じ状態と原因での再試行を進捗と数えない。状態が変わったら再検査できるようにする。
- 人間の編集が必要なら、ファイル・見出し・追記案まで提示する。保護解除、承認の自己生成、利用者設定の自動修復はしない。
- 現在のexit code・既定blocking policyを維持し、JSON拡張は後方互換で設計する。

**成果物:** 代表エラーの診断契約と例、既存コマンドへの導線、拒否→修復→再開のE2E。

**検証:** 設計不足、保護規約の更新、破損設定、古い承認、中断後再開、外部hook競合。正しい拒否とその後の再開を一組で確認する。同じ原因を繰り返す回数、不要な権限要求、利用者ファイル保持を評価する。

### D. 後から「なぜ・何を・どこまで確認したか」を再構成する

**価値:** ログ量ではなく、意思決定と成果物のつながりで追跡可能性を高める。

WI・既存decision log・product差分・実テスト結果・attestationから、変更要約と未確認事項を導出する。作業の記録、申告、実行証拠を別表示する。WI-220の大量の検証記録を、失敗と制約を隠さず短く読むための実例にもできる。

- 手入力の完了台帳を増やさない。派生サマリーは削除しても正本から再生成でき、承認やgateの入力にはしない。
- 実行対象revision/内容digest、環境、失敗・skip・未検証を結び付ける。証拠不足は「不明」とする。
- 会話全文や全Readログを必須保存しない。機密情報を出力せず、保存範囲・保持期間を設計する。

**成果物:** 変更単位の導出サマリーと根拠リンク、既存証拠との対応、鮮度・欠落検査。

**検証:** 新しい読み手が変更理由・上位判断・テスト・残件を特定できるか比較する。旧revisionの成功、自己申告のみ、証拠削除、skip、失敗後の再実行を混ぜても「全て成功」に丸めないことを確認する。

### E. 安全を保ったまま負担を減らす

**価値:** 小さな変更が小さな手間で終わり、既存利用者が安心して更新できる。

Quick Mode・preset・target報告・既存baselineを活かし、どの検査に時間を使い何を省略したか説明できるようにする。新しいモードや巨大なポリシーDSLは増やさない。

- 最初に通常編集の時間内訳を測定する。キャッシュや差分検査は正しさと失効条件を証明できる部分だけに導入する。
- 依存グラフを無視した対象ファイルだけの検査や、unknownを安全とするショートカットをしない。
- 新規診断はまず明示実行または助言で評価する。既存利用者へ新しい強制化を自動適用しない。

**成果物:** 待ち時間の内訳、互換差分レポート、必要性が確認できた最小最適化。

**検証:** warm/cold・Read/OFF/Write、共有依存、設定変更、削除/rename、古いキャッシュ、旧版更新/rollback。速度だけでなく、必要な違反検出と診断到達を同時に確認する。WI-220の絶対500ms未達は維持し、相対改善で置き換えない。

## 4. 進め方

推奨は **評価基盤の固定 → A+Cの小さい縦断実装 → B → D → 計測に基づくE**。Eの計測自体は最初から行う。A〜Eを一度に巨大WIへまとめない。

1. 現行候補・設定・評価課題・判定基準を固定する。WI-220の未達はそのまま保持し、再検証の境界を決める。
2. 最初の実装対象を「一つの変更について、関係する前提と必要な次の行動を根拠付きで説明する読取ビュー」に絞る。新しいblocking、全面的な文書再編、全agentへの自動注入を含めない。
3. A/Cの利用価値を確認した後、Bの共有契約ケースへ拡張する。既存の公開入口・正本・ownerを先に列挙し、重複するものは統合する。
4. Dは既存証跡から作れる範囲で追加する。常設サービス・新しい永続状態・毎操作の全文解析が必要なら費用対効果を再検討する。
5. 各段階の実装前にWIを一意採番し、必要なinception設計とproduct反映を用意する。上位規約の変更が必要なら明示的に相談する。

## 5. 共通の受け入れ方針

以下は次のWIで具体的なfixture・予算と共に確定する提案であり、今回の実測結果ではない。

| 軸 | 測るもの・成立条件 |
|---|---|
| 守るべきもの | 既存の必要拒否、上位承認、正本整合、利用者ファイル保持の回帰を全件維持 |
| 余計に止めない | 固定互換corpusで未承認の新規拒否0。advisory/OFF・旧設定の意味を維持 |
| 復旧できる | 代表する拒否すべてに、許可された修復操作と同一作業の再開経路がある |
| 影響が分かる | 機械判定可能な構造ケースは期待値一致。意味候補のprecision/recall/unknownは別計測し、未知を成功扱いしない |
| agentを邪魔しない | 課題成功率、誤認、手戻り、呼出回数、文字数/計測可能ならtoken、経過時間を旧新比較。警告数削減だけで評価しない |
| 評価を信用できる | 条件と試行数を先に固定し、旧新順序を均衡化。失敗を成功するまで再試行して消さない。少数試行を普遍的保証としない |
| 複雑さを増やさない | 新しい手入力の正本台帳0を原則とし、追加設定・永続状態・hot-path処理をレビュー。削除は利用契約と回帰を確認後 |

将来の複数agent比較は実施時に権限・隔離範囲を確認する。今回は追加agentを実行していない。

## 6. 今はやらないこと

- 全自然言語の意味判定を完成させてから価値を出す進め方。
- LLMの推測をそのままhard blockや上位承認にすること。
- 常に全上位文書をコンテキストへ投入すること。
- 全ファイル・全概念への新しい手動タグ/依存宣言の一括強制。
- 既存のWorld/traceabilityとは別の全体グラフ・承認台帳・ワークフローエンジン。
- 先にドキュメントを大量削除すること。現行仕様・履歴・未達を分離し、根拠を保持して表示を簡潔にする。
- WI-220の未達を別の価値指標で帳消しにしたり、公開可能とみなしたりすること。
