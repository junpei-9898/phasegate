# テスト規約

この文書をテスト規約の正本とする。外部ドキュメントへの依存は置かない。

## 共通ルール

- テスト関連ファイル名は kebab-case にする。
- テストケース名は日本語で、仕様として読める表現にする。
- テストケース名に実装詳細、内部クラス名、変数名、テストデータの都合を混ぜない。
- テストは Arrange / Act / Assert を明確に分ける。
- Act は原則 1 つにする。段階的なライフサイクルを検証する E2E では、各ステップの Act / Assert が読める形にする。
- 実行結果は `actual` に代入する。
- テストの関心外の共通準備はヘルパーやファクトリに寄せる。ただし、各テストの前提が読めなくなるほど隠蔽しない。

## テスト構造

`target` / `describe` / `context` / `it` は以下の役割で使う。

| 要素 | 役割 |
|------|------|
| `target` | テスト対象の機能・関数・ユースケース |
| `describe` | 検証するふるまい |
| `context` | ふるまいが変わる前提条件 |
| `it` | 期待結果 |

```ts
target('validateConfig', () => {
  describe('設定ファイルを検証する', () => {
    context('必須項目が不足している場合', () => {
      it('検証エラーを返すこと', () => {
        // Arrange
        const input = {};

        // Act
        const actual = validateConfig(input);

        // Assert
        expect(actual.valid).toBe(false);
      });
    });
  });
});
```

## モック方針

- ドメインオブジェクトや値オブジェクトは原則として実体を使う。
- モックは外部 I/O、時刻、乱数、プロセス外サービス、Port 実装など、テスト対象が直接制御できない依存に限定する。
- UseCase の単体テストでは Port はモックしてよいが、Domain のふるまいは実体で検証する。
- Page UI テストでバックエンド通信を置き換える場合は MSW などのリクエスト境界でモックする。

## E2E テスト

- E2E はユーザー価値や受け入れ基準として読める名前・手順にする。
- ドメインエキスパート、PdM、CS が読んでも意図が分かる表現にする。
- 同一 Arrange を共有し、前の結果が次の前提になる一連のライフサイクルは 1 つのテストに統合してよい。
- 独立した前提条件を持つケースは分ける。
- テスト固有データは専用 seed やファクトリで管理し、共通データと機能固有データを混ぜない。

## Integration テスト

- 外部から観察できる I/O とふるまいを検証する。
- ケース名は、対象実装を知らない開発者が読んでも入力条件と期待結果が分かる表現にする。
- 独自接頭辞、内部パラメータ名、テストデータ名をケース名に入れない。

## Unit テスト

- 小さなドメインルール、値オブジェクト、サービス、UseCase の分岐を焦点化して検証する。
- 1 テスト 1 ルールを基本とし、境界値や異常系は分ける。
- リファクタリングで壊れないよう、内部実装ではなく外部から見えるふるまいを検証する。

## 禁止例

```ts
// NG: 英語、実装詳細、独自接頭辞、result 変数
it('FAILURE1 - externalUserInfoId is invalid', async () => {
  const result = await sut.execute(input);
  expect(result).toEqual(error);
});
```

```ts
// OK: 日本語で仕様を表し、actual を使う
it('ユーザー識別子が不正な場合は検証エラーを返すこと', async () => {
  const actual = await sut.execute(input);
  expect(actual).toEqual(error);
});
```
