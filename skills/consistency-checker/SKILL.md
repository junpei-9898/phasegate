# Consistency Checker

AIDLCプロセスの全レイヤー設計文書を横断的に検証し、矛盾・漏れ・不整合を検出するスキル。

## 前提条件チェック

### 必須インプット
- **チェック対象の設計文書群** — 存在するレイヤーのみチェック。存在しないレイヤーはスキップ

---

## ⚠️ 3フェーズ実行ルール

**このスキルは3フェーズで実行する。**
- **Phase 1（計画）**: Opus がスコープ・方針・不明点を整理し、人間の承認を得る
- **Phase 2（実行）**: Sonnet 4.6 に委任して成果物を生成する（`scripts/delegate-sonnet.sh` 経由）
- **Phase 3（レビュー）**: Opus が成果物を検証し、問題があれば直接修正する

**Phase 1/2/3を同時に実行してはならない。モデルルーティングの詳細は `docs/principles/model-routing.md` を参照。**

---

## Phase 1: チェック計画（plan）

### 目的
チェック対象・範囲を確認し、人間の承認を得る。

### 出力
会話内で以下を報告する：

```markdown
# 整合性チェック計画

## 1. チェック対象ファイル一覧
| # | レイヤー | ファイルパス | 存在 |
|---|---------|-----------|------|

## 2. 実行するチェック項目
（存在するレイヤーのみ対象）
- [ ] ストーリー↔Unit
- [ ] Unit↔Domain
- [ ] ...

## 3. スキップするチェック項目
（文書が存在しないため）
- ...

## 4. QA（不明点・確認事項）

### [Question] Q1: {質問タイトル}
{質問の詳細と背景}
**推奨案:** {AIの推奨案}

[Answer]
（人間が回答を記入）
```

### Phase 1 完了条件
- チェック計画を報告した
- 不明点がある場合は`[Question]`セクションに記載した
- **人間にボールを渡した**
- **チェック結果はまだ報告していない**

---

## Phase 2: 実行（execution）

### 開始条件
- 人間がPhase 1のチェック計画を承認した

### チェック項目

以下を上位→下位の順で検証する。各チェックの具体的な検証手法は [references/チェックリスト.md](references/チェックリスト.md) を参照。

1. **ストーリー↔Unit** — 全ストーリーがいずれかのUnitに所属しているか
2. **Unit↔Domain** — 全Unitの業務概念がドメインモデルに定義されているか
3. **Domain↔論理設計** — 全集約/リポジトリに対応するコンポーネントがあるか
4. **論理設計↔環境設計** — 全サービス/DB変更が環境設計に列挙されているか
5. **環境設計↔実装** — 環境設計の制約が実装に反映されているか
6. **マイグレーション台帳↔実ファイル** — 台帳のエントリと実ファイルが一致しているか
7. **制約集↔実装** — フレームワーク制約集のルールがコードで遵守されているか

### Phase 2 最低出力基準（Sonnet委任時の品質制約）

以下の基準を満たさない出力は不完全とみなし、Phase 3レビューでBLOCKとする。

| 基準 | 最低要件 |
|------|---------|
| チェック項目網羅 | Phase 1で計画した全チェック項目が実行されていること |
| 具体的な不整合記述 | 検出された不整合に具体的なファイル名・行・内容が記載されていること |
| 重要度判定 | 各不整合に重要度（高/中/低）が付与されていること |
| 推奨アクション | 各不整合に対する具体的な修正アクションが提案されていること |
| スキップ理由 | スキップしたチェック項目にスキップ理由が記載されていること |

### 出力フォーマット

```markdown
# 整合性チェック結果

## 検出された不整合

| # | レイヤー間 | 不整合内容 | 重要度 | 推奨アクション |
|---|----------|----------|--------|-------------|

## チェック対象外（スキップ）
- ...

## サマリー
- チェック対象レイヤー数: N
- 不整合件数: N
```

## Phase 3: レビュー（Opus review）

### 実行主体
メインセッション（Opus 4.6）が実行する。Sonnetへの再委任は行わない。

### レビュー手順
1. Sonnetが出力したファイルを読み込む
2. `docs/principles/model-routing.md` のレビュー観点 R1〜R7 に沿って検証する
3. **スキル固有レビュー観点**を検証する
4. 判定結果を出力する

### スキル固有レビュー観点（BLOCK基準）
- [ ] Phase 1で計画した全チェック項目が実行されているか
- [ ] 不整合の記述が具体的か（曖昧な「不一致あり」だけでないか）
- [ ] 重要度の判定基準が一貫しているか
- [ ] 推奨アクションが実行可能か（対応スキル名が明記されているか）
- [ ] 偽陰性がないか（明らかな不整合を見逃していないか）

### engineering-perspective レビュー観点（WARN基準）
- [ ] ドメインスメル（責務混在・言語の乖離・境界不明確）がレイヤー横断で検出されているか
- [ ] SOLID違反（SRP・DIP）が設計レイヤー間で見逃されていないか
- [ ] コードスメル（Shotgun Surgery等）の兆候が設計変更の波及パターンから検出されているか

### 判定と修正
- **BLOCK項目にFAIL** → Opusが直接修正してから完了とする
- **WARNのみFAIL** → Opusが直接修正してから完了とする
- **全PASS** → 完了

## 注意事項

- 不整合の修正は行わず、検出と推奨アクションの提示に徹する
- 技術スタック固有の用語は使わず、汎用的な表現でチェックする
