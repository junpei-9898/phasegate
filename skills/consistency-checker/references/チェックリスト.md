# 整合性チェック 検証手法ガイド

各チェック項目の汎用的な検証手法。技術スタックに依存しない。

## 1. ストーリー ↔ Unit

**手法:** ストーリーIDの全数マッチング

1. ストーリー一覧からストーリーIDを全て抽出する
2. 各Unit定義ファイルからストーリーID参照を全て抽出する
3. ストーリー一覧にあるがUnit定義に無いID = 孤立ストーリー

## 2. Unit ↔ Domain

**手法:** 業務概念のクロスリファレンス

1. 各Unit定義から主要な業務名詞（エンティティ候補）を抽出する
2. ドメインモデルの集約・エンティティ・値オブジェクト名と照合する
3. Unit定義に登場するがドメインモデルに未定義の業務名詞 = 漏れ

## 3. Domain ↔ 論理設計

**手法:** 集約→コンポーネント対応表の照合

1. ドメインモデルから集約名・リポジトリインターフェース名を抽出する
2. 論理設計からコンポーネント名（コントローラ、ユースケース、リポジトリ実装等）を抽出する
3. ドメインモデルの集約に対応するコンポーネントが論理設計に無い = 漏れ

## 4. 論理設計 ↔ 環境設計

**手法:** インフラ要件の突合

1. 論理設計から以下を抽出する:
   - 新規サービス/関数の定義
   - 新規テーブル/ビュー/マイグレーションの定義
   - 外部連携・認証に関する記述
2. 環境設計の各セクションと突合する:
   - サービス構成マニフェストに全サービスが列挙されているか
   - マイグレーション台帳に全DB変更が記載されているか

## 5. 環境設計 ↔ 実装

**手法:** 設定ファイルとコードの機械的照合

1. 環境設計のマイグレーション台帳からファイル名を抽出 → 実ファイルの存在確認
2. 環境設計のサービス構成から設定項目を抽出 → 設定ファイルとの照合
3. 環境設計のフレームワーク制約集からルールを抽出 → コード内のパターン検索

## 汎用検索パターン例

```
# ストーリーID抽出（マークダウンテーブルから）
grep -oE 'US-[0-9]+|US-DEV-[0-9]+' docs/product/user_stories.md

# Unit内のストーリー参照抽出
grep -oE 'US-[0-9]+|US-DEV-[0-9]+' docs/product/units/*.md

# ドメインモデルの集約名抽出
grep -E '^### .+集約|Aggregate' docs/product/construction/*/domain_model.md
```
