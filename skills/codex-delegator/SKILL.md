# Codex Delegator

codex CLI（gpt-5.4）にタスクをLocal実行で並列委任し、2段階レビューで品質管理するスキル。Claude Codeは**マネージャー**、codexは**実行者**、Sonnetは**レビュワー**として振る舞う。

## 前提

- codex CLI v0.111.0+（`codex exec "<prompt>" --full-auto`）
- モデル: `gpt-5.4`（ChatGPTアカウントでは派生モデル不可）
- プロジェクト規約: `docs/principles/testing-rules.md`, `docs/principles/architecture-philosophy.md`
- 設計文書が揃っていることが前提（ドメインモデル、論理設計、テストケース設計等）

## 核心原則

1. **codexに判断させない**: 何を・どのファイルに・どのパターンで作るかはClaude Codeが決定する。codexは具体的指示の実行者
2. **設計文書との突合がレビューの主軸**: `pnpm test` グリーンだけでは不十分。設計文書のケースID・期待値との一致を検証する
3. **早期フォールバック**: codexが2回失敗したらClaude Codeが直接実装に切り替える
4. **Local実行のみ**: codex cloud / @codex review は使用しない。全タスクを `codex exec --full-auto` で実行する
5. **レビューはdiffベース**: 生成物の全文Readではなく、`git diff` の差分をレビュー入力とする。コンテキストウィンドウを節約し、変更点に集中する

---

## 実行モデル

全タスクを **codex Local** で実行する。

```bash
codex exec "<プロンプト>" --full-auto
```

### コミット前の自己点検

codex対話モード内で `/review` を使用してコミット前にざっくり点検できる。

```bash
codex                # 対話モード起動
/review              # ワーキングツリーの変更を点検
/review Focus on edge cases and security issues  # 観点指定
```

### 粒度の制御

Local実行では1委任単位の粒度を小さく保つことがコスト効率上重要。

| 基準 | 推奨値 |
|------|-------|
| 変更ファイル数 | 3-5個以下 |
| 生成行数 | 200行以下 |
| 所要時間目安 | 5-15分 |

粒度が大きすぎるタスクは分割する。分割してもLocal枠の消費が増えるだけなので、**品質が上がるなら迷わず分割する**。

## Phase 1: 計画（Plan）

### Step 1.1: タスク分解

ユーザーの指示を**委任単位（Delegation Unit）**に分解する。分解基準:

| 基準 | 内容 |
|------|------|
| ファイル独立性 | 出力ファイルが重複しない |
| 入力独立性 | 他の委任単位の出力を必要としない |
| 粒度上限 | 1単位あたり変更ファイル3-5個以下、生成200行以下 |

並列可能な単位は Wave にグループ化する。共有ファイル（barrel export等）への変更が必要なタスクは直列化する。

### Step 1.2: タスクタイプ判定

各委任単位にタスクタイプを付与し、適用するレビュー次元を決定する:

| タスクタイプ | 判定基準 | 追加レビュー次元 |
|------------|---------|----------------|
| `design-plan` | inception配下の `*_plan.md` | 上位文書整合、QAセクション、配置ルール |
| `design-doc` | construction配下の設計 `.md` | 計画との整合、アーキテクチャ原則、トレーサビリティ |
| `implementation` | `.ts` 等のコード | テスト規約、レイヤー依存方向、型安全性 |
| `test` | テストコード | ケース網羅、設計文書突合、テスト独立性 |

### Step 1.3: プロンプト設計

各委任単位のプロンプトを3層構造で構成する。詳細テンプレートは [references/prompt-patterns.md](references/prompt-patterns.md) を参照。

```
[コンテキスト層] 読むべきファイルパス + 関連ルールの具体的引用
[タスク層]       作業内容、入力ファイル、出力ファイルパスと期待フォーマット
[制約層]         変更許可ファイルのホワイトリスト、スコープ制限
```

**重要**: 「既存コードのパターンに従え」ではなく、具体的なパターンのコード例をインラインで添付する。

**プロンプト長の判断**: 2000文字以下なら直接引数、超える場合は一時ファイルに書き出す。

### Step 1.4: 計画出力

以下のフォーマットで報告し、人間の承認を待つ:

```markdown
## Codex委任計画

### タスク分解
| # | 委任単位 | タスクタイプ | Wave | 出力ファイル |
|---|---------|------------|------|------------|

### 実行順序
- Wave 1（並列）: A, B, C
- Wave 2（Wave 1完了後）: D, E

### レビュー次元
コア次元（C1-C4）+ タスクタイプ別次元を適用

### QA
[Question] Q1: ...
```

### Phase 1 完了条件

- 計画を報告した
- 人間にボールを渡した
- **codex exec はまだ実行していない**

## Phase 2: 実行（Execute）

### 開始条件

- 人間がPhase 1の計画を承認した
- QAに全て回答済み（QAがある場合）

### Step A: 委任（Delegate）

Wave単位で Agent tool を使用し並列実行する。

```bash
# 各Agent内で実行
codex exec "<プロンプト>" --full-auto
```

**並列度上限**: 同時実行は最大3タスク（レート制限考慮）。

**実行結果の追跡**:

```
| # | 委任単位 | 状態 | 出力ファイル |
|---|---------|------|------------|
| 1 | A       | completed | path/to/file.ts |
| 2 | B       | failed    | (エラー内容) |
```

**部分成功時**: 成功したタスクの結果は保持し、失敗分のみ再実行する。

### Step B: レビュー（2段階Review）

レビューは **Tier 1（機械的チェック）→ Tier 2（Sonnetによる設計突合）** の2段階で実行する。Tier 1でBLOCKが出た場合はTier 2に進まず即REJECTし、コンテキストを節約する。

#### Step B.0: 差分抽出

レビュー入力は**全文Readではなくdiff**を使う。

```bash
# 変更ファイル一覧
git diff --stat HEAD~1
# 変更内容（diffベース）
git diff HEAD~1
# スコープ外変更の検出
git diff --name-only HEAD~1
```

#### Step B.1: Tier 1 — 機械的チェック（スクリプト/grep）

Claude Codeがgrep・スクリプトで自動検証する。人間の判断不要な項目を高速に処理する。

| ID | 次元 | 検証方法 | 重大度 |
|----|------|---------|--------|
| C1 | スコープ遵守 | `git diff --name-only` と指示ファイルリストの差分比較 | BLOCK |
| C2 | 既存破壊なし | `pnpm test` 実行（既存テスト全パス確認） | BLOCK |
| C3 | 命名一貫性 | grep: 日本語テスト名、`actual`変数、target/context構造 | BLOCK |
| IM3 | レイヤー違反なし | grep: domain層ファイルからinfrastructure層へのimport検出 | BLOCK |
| IM4 | 型安全性 | grep: 正当理由なき `any` / `as` の使用検出 | WARN |
| TE1 | ケースID突合 | 設計文書のケースIDリスト vs テストファイル内のID（diff抽出） | BLOCK |
| DP3 | 配置ルール準拠 | `git diff --name-only` とfolder_management_rules.mdのパス照合 | BLOCK |

**Tier 1 判定**:
```
BLOCK が1つでもFAIL → REJECT（Tier 2スキップ）→ Step Cへ
全PASS or WARNのみ  → Tier 2へ進む
```

#### Step B.2: Tier 2 — Sonnetによる設計突合チェック

Agent tool（subagent_type未指定）でSonnetに以下の**最小限の入力**を渡してレビューさせる。

**Tier 2への入力（これだけ）**:
1. `git diff HEAD~1` の出力（変更差分のみ）
2. Tier 1の結果サマリ（PASS/WARN一覧）
3. 設計文書の**該当箇所の抜粋**（全文ではない）

**Tier 2 レビュー次元**:

| ID | 次元 | 検証内容 | 重大度 |
|----|------|---------|--------|
| C4 | 完了度 | 指示項目の欠落がないか | BLOCK |
| DD1 | 計画との整合 | diffの内容が設計文書の方針と矛盾しないか | BLOCK |
| DD2 | アーキテクチャ原則 | ヘキサゴナル・DDD原則に沿っているか | BLOCK |
| DD4/IM-Y | YAGNI | 指示範囲外の「改善」「リファクタ」「将来への備え」がないか | BLOCK |
| IM5 | DRY | 新規コードに既存コードとの重複がないか | WARN |
| TE2 | 期待値突合 | Assertionの期待値が設計文書の期待結果と一致するか | BLOCK |
| DD3 | トレーサビリティ | 各要素がストーリー/Unit要件に紐づいているか | WARN |

詳細は [references/review-dimensions.md](references/review-dimensions.md) を参照。

**Tier 2 判定**:
```
BLOCK が1つでもFAIL → REJECT → Step Cへ
WARN のみ FAIL      → CONDITIONAL_PASS（WARNをまとめて修正）
全PASS               → PASS（完了）
```

### Step C: 修正ループ（Fix Loop）

#### 修正方針の判定

| 条件 | アクション |
|------|----------|
| FAIL箇所が3箇所以下かつ局所的 | Claude Codeが自己修正 |
| 4箇所以上または構造的問題 | codexに修正指示を再委任 |
| 同一次元で2回連続FAIL | Claude Codeが自己修正に切替 |

#### 修正指示の構造（codex再委任時）

```
## 修正指示（Round N）

### 前回レビュー結果
- FAIL次元: {ID}: {名前}

### 修正箇所
#### [{次元ID}] {ファイルパス}:{行番号}
- 現状: {問題の具体的記述}
- 期待: {あるべき状態}
- 修正方法: {具体的手順}

### 制約
- 修正対象以外のコードに手を加えないこと
```

#### エスカレーション条件

以下のいずれかでループ終了:

| 条件 | アクション |
|------|----------|
| 同一ファイルに2回修正してもBLOCK解消せず | Claude Codeが直接修正 |
| 修正が新たなBLOCKを生み出す（退行） | Claude Codeが直接修正 |
| 修正対象がスコープ外に波及 | 人間にエスカレーション |

エスカレーション時は以下を報告:

```markdown
## エスカレーション

| ファイル | 問題 | 試行回数 |
|---------|------|---------|

### 選択肢
1. Claude Codeが直接修正（推奨）
2. タスク分解を見直して再委任
3. 設計文書を修正してから再実行
4. Opusにレビューを依頼（設計自体を疑う必要がある場合）
```

## エラーハンドリング

### codex exec 実行失敗

| エラー種別 | 対策 |
|-----------|------|
| タイムアウト | タスクを分割して再実行 |
| レート制限 | 並列度を下げて再試行（最大3回） |
| 認証切れ | 人間にエスカレーション |
| 出力が完全に誤り（言語違い等） | プロンプトを再設計して再実行（修正ではなく新規実行） |

### 修正主体の判断基準

| Claude Codeが直接修正 | codexに再委任 | 人間にエスカレーション |
|---------------------|-------------|---------------------|
| typo、import修正、コメント追加 | ロジック修正、新規メソッド追加 | 設計文書との矛盾、レイヤー違反 |
| テストケース名の日本語化 | 構造的な書き直し | 集約の責務変更 |
| WARN項目の軽微な修正 | 4箇所以上のBLOCK | スコープ外への波及 |

---

## 注意事項

- codex CLIはChatGPTアカウントでは `gpt-5.4` のみ使用可能
- `--full-auto` モードでのファイルシステム変更に注意。実行後に `git diff --stat` で想定外の変更がないか確認する
- 設計スキルとして使用する場合、コード生成は行わない（設計文書のみ出力）
- **ファイル配置は `docs/folder_management_rules.md` に従う**
- codexへのプロンプトでは「読むべきファイル」だけでなく「そこから抽出した具体パターン」をインライン引用する
- `/review` はコミット前の自己点検用。codex対話モード内で使用する
