# 層別判定ガイド

変更・発見の種類ごとに、どのレイヤーの設計文書を更新すべきかの判定基準と具体例。

## 環境設計に帰属するもの（最も頻度が高い）

**判定基準:** コードの正しさではなく、環境の正しさに関する問題

| パターン | 例 |
|---------|-----|
| 設定ファイルの漏れ | サービス/関数が設定ファイルに未登録 |
| ランタイム制約 | 認証トークンのアルゴリズム不一致 |
| フレームワーク制約 | 特定ファイルからのexportルール、ビルド制約 |
| シードデータ不足 | テストに必要なデータ層の欠落 |
| マイグレーション漏れ | DB変更が適用されていない |
| 依存関係管理 | import map、パッケージ設定の不備 |

## 論理設計に帰属するもの

**判定基準:** コンポーネントの分割・連携・責務に関する問題

| パターン | 例 |
|---------|-----|
| API契約の変更 | レスポンス形式では画面要件を満たせない |
| 層の責務違反 | BFF層にドメインロジックが混入 |
| コンポーネント不足 | 必要なミドルウェア/ハンドラが未設計 |
| テーブル設計の変更 | カラム追加/インデックス変更が必要 |

## Domainに帰属するもの

**判定基準:** ビジネスルール・業務概念の理解に関する問題

| パターン | 例 |
|---------|-----|
| エンティティの不足 | 必要な業務概念がモデル化されていない |
| 集約境界の誤り | 本来別の集約であるべきものが混在 |
| 状態遷移の不足 | 必要なドメインイベントが未定義 |
| 不変条件の誤り | ビジネスルールの理解が間違っていた |

## ストーリー/Unitに帰属するもの（非常にまれ）

**判定基準:** そもそも何を作るかの理解に関する問題

| パターン | 例 |
|---------|-----|
| ストーリーの漏れ | 必要な機能がストーリーとして定義されていない |
| Unit分割の問題 | 密結合すぎて独立実装できない |
| 受け入れ基準の不足 | 検証不能な基準しかない |

## 判定フローチャート

```
発見の内容は？
├─ 「コードは正しいが動かない」→ 環境設計
├─ 「コンポーネントの連携が間違っている」→ 論理設計
├─ 「業務ルールの理解が違った」→ Domain
└─ 「そもそも作るべきものが違った」→ ストーリー/Unit
```
